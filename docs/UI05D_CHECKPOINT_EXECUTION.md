# UI-05d parts 4g/4h — exact checkpoint receipts and explicit discard
Combined related execution subtasks after reconstructing storage history through 3b51d5f. Contracts come from native checkpoint storage 8af8f85, persisted reconciliation 75deb68, loader c29e5f1, action planner 0db4421 and revision planner 3b51d5f. This delivery uses none of the incompatible legacy 3d/4a/4b path.
checkpoint-save.ts captures/validates an owned native checkpoint and an explicit expectedRevision (null for first revision). It exposes getCheckpoint/getSnapshot/subscribe/save. Creating a controller writes nothing. Only explicit save() calls the supplied initialized repository. Ready/saving/saved/unconfirmed/conflict states remain separate, receipts must match the captured session/revision and saved/already_saved status, and concurrent/reentrant calls share a promise assigned before listener publication. Listener exceptions do not change receipts. Saved/conflicted controllers do not write again; unconfirmed retries retain exactly the same checkpoint, revision, time and expectedRevision. No replacement IDs, inferred timestamps or re-planned revision bypass a conflict.
prepareReceiptRevisionSaveController combines fresh receipt reconciliation/revision planning with controller creation. Blocked/unchanged plans return controller=null. A proposed revision returns a ready controller, never an automatic save. The general controller also supports initial checkpoints and later app-owned checkpoint captures; future UI orchestration must sequence revisions and retain uncertain proposals instead of creating competing revisions. A saved receipt confirms a particular historical checkpoint write, not continued currentness or resume permission.
recovery-discard.ts requires explicit confirmation bound to the exact session/revision before any reads/writes. It obtains a fresh discard plan, then calls discardCheckpoint with expectedRevision. Missing/stale targets block, final repository conflicts remain conflicts and uncertain write failures are unconfirmed rather than called discarded. A later explicit retry of the same target can obtain already_discarded. Planning/read errors reject before a discard write. No attempt, pending record or checkpoint snapshot is deleted, and completed/discarded outboxes remain separate from session resumption. Confirmation is UI intent, not authentication or an authorization token; callers must not manufacture it before a user confirms.
Neither module opens a database or starts background retries. Supplying an initialized repository is the app's responsibility; opening it elsewhere can migrate storage. Operations are not executed while preparing/pushing source. There is no resume executor, content policy provider, controller restoration call, attempt append or screen integration in this delivery. The repository remains the final transaction/idempotency/discard/revision gate. Cross-controller/process writes may race; uncertainty does not permit silent overwrite or changing retry content.
Only two new source modules and these notes are added. Existing controllers/planners/loader/decoders/builders/repository/schema/screens/fixtures/dependencies/workflows are unchanged. No UI invokes the new execution functions yet and normal app use still lacks checkpoint capture/restart recovery.
