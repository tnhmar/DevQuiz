# UI-05c part 1 — stable save jobs and status controls
Adds shared source before wiring either practice screen. Expo Crypto UUIDs replace process-local timestamp IDs when future callers adopt newPracticeSessionId. Record preparation creates one UUID and recordedAt per logical outcome, captures the UI-05a record once and retains it in a module-memory job. Repeated preparation in that process returns the same job; save retries reuse the same immutable record, including timestamps and snapshot strings. No fallback counter IDs or new attempt IDs are generated to bypass a conflict.
A controller exposes a cached immutable snapshot plus subscribe/save functions. Concurrent save calls share the pending promise. Ready, saving, confirmed saved, unconfirmed and conflict states remain distinct. A failed acknowledgement does not prove that no write occurred; unconfirmed retries can obtain already_saved from UI-05b. A conflict is terminal for this job and never invokes overwrite/replacement logic. UI listeners cannot change the storage outcome. The controlled save card subscribes through React useSyncExternalStore and explicitly distinguishes saved fixture history from learning progress, and subjective self-ratings from objective choice scoring.
Jobs are process-memory outbox entries, not durable checkpoints. They may be lost on app restart and currently remain retained for the module lifetime without a cleanup/quota policy. UUID generation alone does not make an unsaved response durable. Pending writes can finish after a screen unmounts without updating that screen's React state; source recovery/receipt reconciliation still requires later work. Native storage rejects unsupported platforms, and errors are not relabelled as saved.
Next small commits wire choice submission and open rubric completion to these jobs, adopt UUID session/restart IDs and update all affected saved-history wording. Record preparation failures must be shown separately and cannot be called saved. Screens still do not use this controller/card in this commit, still create their old session IDs and still save nothing. Interim open answer checkpoints, exposure/retry history and restart recovery remain pending.
Only the controller, save-status card and these notes are added. Existing builders/repository/schema, screens, engines, fixture JSON, dependencies and workflows are unchanged. No progress/evidence aggregation, AI grading or automated authoring is added.
API references consulted: https://docs.expo.dev/versions/latest/sdk/crypto/ and https://react.dev/reference/react/useSyncExternalStore . No repository reads, verification, schema/syntax checks, typechecking, tests, builds, CI inspection, device runs, database opens/migrations/writes or UUID generation were performed during preparation; none will be performed after pushing. API/package compatibility and runtime behavior remain unverified.
