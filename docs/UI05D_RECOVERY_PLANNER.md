# UI-05d part 4e — explicit fresh-read recovery action planning
Reconstructed the latest storage state through c29e5f1 from commit history and available source patches. The planner uses the actual persisted-format loader/reconciliation from 75deb68/c29e5f1 and the native repository revision/discard semantics from 8af8f85. It does not use legacy recovery-checkpoint.ts, validate-checkpoint.ts or resume-eligibility.ts.
prepareRecoveryAction takes the session ID, revision displayed to the user and explicit resume/discard intent. It performs a fresh targeted load with complete saved-record reconciliation, requires the requested revision and returns an immutable blocked/resume/discard plan. Missing/stale targets do not get silently replaced with a newer revision. Loader/read/conflict/invalid-policy failures reject instead of being relabelled eligible or missing.
Resume requires active/non-discarded/nonempty state plus an explicit asynchronous content/access policy evaluation against the decoded pinned checkpoint. Missing policy is blocked; denied policy has a bounded reason. Allow decisions distinguish fixture-preview from approved-content, and the captured fixture bit must agree. Zero pending records does not block a valid session. Completed/discarded sessions cannot be resumed, although their outstanding records remain recoverable through the separate outbox path.
The policy evaluator is trusted application code, not an imported flag or a content assertion. It must actually resolve content availability, current access, revision compatibility, editorial/publication and factual verification requirements as applicable; the planner cannot establish those facts from captured approval fields. An allow result is not supplied by default and no policy provider/catalogue activation is implemented here. Fixture preview must remain explicitly labelled and cannot promote fixture answers into objective learning evidence.
After an allow decision, the planner rereads the checkpoint and requires identical serialized state/discard context. Discard planning also rereads and retains all embedded pending record IDs, including already-confirmed records awaiting checkpoint reconciliation. It neither deletes attempts/outboxes nor infers user confirmation. Already-discarded matching targets return an explicit idempotent discard plan; completed checkpoints may be deliberately discarded without erasing history. Invalid checkpoints cannot be bypassed by this planner's strict load gate; separate diagnostics/manual lifecycle work remains necessary.
A plan is not an authorization token or a transaction-wide guarantee. Content policy/checkpoint/receipt state can change after return. Execution must obtain a fresh plan, honour expectedRevision, require explicit UI confirmation for discard and use the final repository checks. No maximum resume age, guessed timestamps, fabricated receipt or unconditional pending-record requirement is introduced.
Only this new planner and notes are added. It does not open storage, call discardCheckpoint/saveCheckpoint/append/save(), register controllers, submit/restart/resume an engine, modify UI state or schedule background work. Existing loader/controller/decoders/builders/repository/schema/screens/fixtures/dependencies/workflows are unchanged. No UI calls this function yet.
