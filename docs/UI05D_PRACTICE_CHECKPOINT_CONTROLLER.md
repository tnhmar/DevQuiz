# UI-05d practice checkpoint capture controller
Adds a per-session serialized controller over the existing checkpoint builders and repository contract. It gathers no IDs and opens no database. Callers provide the same session state, exact pending immutable AttemptRecords and a real capture timestamp; createChoiceCheckpoint/createOpenCheckpoint remain the ownership validators.
Only one checkpoint revision is in flight. Additional state changes are coalesced to the latest queued builder and, after a confirmed receipt, become the next single revision. Unconfirmed saves retain the exact proposed checkpoint and expectedRevision; later state is not allowed to silently advance it until retry/reconciliation resolves ambiguity. A conflict is terminal for this controller instance and cannot be bypassed by changing revision/identity. `retryExact` reuses the exact object/revision/timestamp and relies on repository idempotency.
The captured state and persistence receipt are separate statuses. No `save()` of attempt records, engine submit/next/restart, resume, discard, timeout, polling or automatic retry occurs. The caller decides when `captureChoice`/`captureOpen` runs and must pass current retained records from the save-controller registry plus any preserved earlier retry records. Capture failures remain the caller's responsibility. This controller does not itself make text keystrokes durable; screen/lifecycle wiring and scheduling are a separate step.
Current limitations: a queued capture is a closure over caller-provided values, so callers must pass immutable engine states/selection/record arrays (these engine values are treated as immutable by contract). A sequence of capture calls while one write is pending resolves to the in-flight receipt; caller should recapture latest state after receipt or subscribe to the controller state. This first component intentionally does not expose the queued closure as a promise for the later revision, to avoid duplicate/concurrent writes. UI needs a clear “latest state pending” indicator and a post-receipt drain trigger, which is a follow-up before relying on coalescing for durability.
Only this new controller and notes are added. Engines, screen files, checkpoint builders, storage schema/repository, save controllers, loader/planners, navigation, fixtures, dependencies and workflows are unchanged. No screen uses this controller yet.
Done in source: checkpoint/outbox persistence, exact saved-record reconciliation and read/plan/write primitives; this controller adds ordered in-process capture.
