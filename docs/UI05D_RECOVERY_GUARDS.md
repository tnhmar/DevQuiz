# UI-05d part 3a — bounded parsing and question/block guards
Starts strict restore decoding with reusable primitive/object guards and typed question/block snapshot checks. It adds no dependency and does not use a content-supplied schema. JSON input is limited to 16000000 characters, depth 64, 250000 visited values and 10000 members per generic container; typed block/question checks apply narrower native collection/text bounds. These are explicit first-version recovery limits, not a claim that all possible authoring packages fit them.
Exact object keys, primitive types, IDs, enums, option/criterion uniqueness, correct-option references and scoring method shapes are checked. All eight block/four inline variants retain literal content; code whitespace and explicit alternatives are preserved. Boolean canonical IDs/order and objective=false open scoring are enforced. Structural approval metadata remains data, not permission to activate content or declare factual verification. Table row-width inconsistency remains compatible with the reader's text-alternative fallback rather than being silently repaired.
Guards do not coerce values, populate defaults, execute code, resolve external references or rewrite stored snapshots. These helpers are only called by later restore code. The small accepted TypeScript cast at the end of a question/block decoder follows its runtime shape checks; it is not a substitute for pending phase/history/record checks. Decoded nested objects are not frozen by these shape guards alone; the later restore decoder must own/freeze/reconstruct state safely.
Next decoder commits validate choice phase/index/committed-answer order and confidence/help history, then open writing/rating/finished consistency and locked response/confidence, followed by exact pending-record reconciliation. They must reject unsupported engine versions and restore without generating IDs, regrading outcomes into new events, resubmitting writing or promoting fixtures/self-ratings. Prototype-safe map reconstruction, cross-record identity and publication/activation policy remain required before resume.
Only the new guard/question decoder modules and these notes are added. Existing snapshot builders, schema/repository/controller, engines, screens, fixtures, dependencies and workflows are unchanged. No recovery is wired, no snapshot is parsed during preparation and no database is read or written. UI pending jobs remain memory-only until checkpoint wiring.
Existing block/schema contracts were read through their source commit diff. No verification, schema/syntax checks, typechecking, tests, builds, CI inspection, device runs, UUID generation, JSON parsing/validation execution or database operations were performed during preparation; none will be performed after pushing. Contract fidelity, compatibility and runtime behavior remain unverified.
