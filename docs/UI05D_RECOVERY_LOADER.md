# UI-05d part 4d — read-only repository recovery loading
Storage history through fb554e8 confirms the repository contracts introduced by 920aa1f/8af8f85, native checkpoint builders from cce074f, corrected persisted decoder from 75deb68 and controller rehydration from fb554e8. This module uses the real repository's findCheckpoint/listCheckpoints/findById methods through a read-only Pick; it imports the repository only as a type. There is no openAttemptRepository call or migration in this module. The application must supply an initialized trusted repository; opening it elsewhere may initialize/migrate storage and is not made read-only by this adapter.
loadRecoverySession captures the returned StoredCheckpoint as JSON, decodes it before making attempt lookups, requires the requested session identity, obtains one successful findById observation per pending record and performs exact reconciliation. A rejected lookup is never represented as null/no-row. Missing checkpoints return null; invalid/incompatible/conflicting data or failed reads reject. It rereads the checkpoint after reconciliation and rejects any change to its serialized projection or separate discard flag. Snapshot strings and record identities/times remain unchanged.
The immutable result retains serialized checkpoint/observations for the explicit 4c restoration step and separate sessionCandidate/hasOutstanding flags. Candidate means structurally active, non-discarded and nonempty, not authorized, approved, current-content-compatible or eligible to resume. No pending record is required to be a candidate. Completed/discarded sessions are not candidates but their outboxes still reconcile. Pending rows already saved may remain in the persisted outbox until a later revision write; hasOutstanding distinguishes them without silently dropping the persisted records.
loadRecoveryPage supports separate resumable/outbox repository queries with a default page size of 20 and maximum 100. It reloads each listed session, preserves per-session failures as explicit changed-or-unavailable blocked entries and continues with other sessions. Initial listing failure rejects the page rather than appearing empty. Duplicate/invalid listed identities and excess page size reject. Generic errors are not logged with private answers. nextOffset follows consumed listing rows; mayHaveMore is only a full-page hint, not proof another page exists.
Reads are sequential and bounded per page, but not a single transaction or a consistent cross-page snapshot. Concurrent writes after the final reread remain possible; offset pagination may shift and callers must refresh/deduplicate by session ID. Resume/discard/revision writes require a fresh targeted read and expectedRevision checks. Saved-record lookups can race with append; the append-only repository remains the final idempotency/conflict guard. Read failures, conflicts and unsupported formats all block the affected entry; nothing is automatically discarded, repaired or labelled saved.
Only this new module and notes are added. It does not register controllers, call save(), submit an answer, resume an engine, save/revise/discard a checkpoint or start retries/timers. The 4c adapter remains an explicit later call; the UI currently calls neither loader nor restoration. Existing modules, screens, builders, repository/schema, fixtures, dependencies and workflows are unchanged. The incompatible legacy 3d/4a/4b modules are not used.
