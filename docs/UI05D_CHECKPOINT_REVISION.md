prepareCheckpointReceiptRevision accepts the displayed session/revision and an explicit caller-supplied capture time. It reloads the actual checkpoint and all pending saved-record observations. Missing or changed targets block. Discarded checkpoints block because the current repository rejects all subsequent writes under their ID; their outboxes can still be reconciled/retried separately and are not silently erased. Completed non-discarded checkpoints may have their outboxes reconciled without becoming active.
If no exact pending record is confirmed saved, the result is unchanged: no new revision or timestamp is assigned. Otherwise the capture time must not precede the old checkpoint time, revision must fit safe-integer bounds, and the proposed revision advances exactly one. A backwards clock is blocked, not repaired with a guessed time. The caller must supply a real capture time for the proposed projection; no Date.now/UUID generation occurs here.
Only exactly matched immutable attempt rows are removed from the proposed pending array. Retained records come from the original parsed checkpoint body in original order, including original payloadJson/technologyScopesJson strings and record IDs/times. The payload is kept intact as parsed data, not rebuilt from decoded engine state, reselected questions or a newer content bank. The enclosing JSON is serialized again, so its whitespace/escaping can change; the engine/payload values and nested attempt snapshot strings are not rewritten. Session, kind, fixture and active/completed status remain unchanged.
The proposed header/body is checked with the native persisted decoder, and the source checkpoint is reread before returning the immutable save-checkpoint plan. It carries expectedRevision, sourceStoredJson, removed IDs and retained IDs. Read/decode/conflict failures reject, never appear confirmed. Execution must obtain fresh intent/source checks and call saveCheckpoint with expectedRevision; the repository transaction verifies removed records still exactly exist and rejects stale revisions/discard revival. A plan is not a storage receipt or a transaction-wide snapshot. Idempotent retry must retain the identical proposed checkpoint, revision and capture time rather than make another revision.
