# UI-05d part 1 — recovery snapshot foundation
Defines versioned, primitive-only frozen checkpoint records, separate from immutable attempt history. Choice snapshots serialize the full selected engine state, question definitions/order, option selection, confidence/help signals, committed answers, hint registry and local retry context plus selection settings. Open snapshots serialize writing/rating/finished state, original/locked text, submitted confidence, rubric ratings and finalized result when present. This first builder does not restore or resubmit anything.
Caller supplies a monotonically advancing revision, capture time and exact pending AttemptRecords for the same session. Builders check basic ownership/order/commit identity and serialize those records without generating replacement IDs or timestamps. Completed sessions may still have pending records; future startup recovery must reconcile those writes rather than hide them because the session is completed. Confirmed attempts must not be regraded or rewritten from newer content.
Snapshots use engineVersion/format markers to support an explicit future compatibility check. These builders consume trusted app-owned engine data, not arbitrary imported JSON. A strict restore decoder with state/content consistency checks, safe hint-registry reconstruction, unsupported-version handling and pending-record receipt reconciliation is required before restored data can reach the engines. JSON.parse plus a TypeScript assertion alone is not a restore gate or publication permission.
Storage will keep latest session checkpoints separate from append-only attempts, reject stale/conflicting revisions and distinguish discard/complete from deleting answer history. A checkpoint is durable only after an acknowledged storage write; the current module itself persists nothing. Restoring writing/rating must not commit a new answer, reveal a model answer before the locked phase, infer confidence or turn subjective outcomes into objective evidence.
Next small tasks: SQLite v2 checkpoint/outbox storage; expose the exact captured controller records for checkpointing; strict decoder/reconciliation; screen checkpoint receipts and resume/discard controls. Earlier retry-session jobs and capture failures need their own preserved state/adapter and are not automatically included by passing the current engine alone. Current-session choice capture failures remain represented in engine.answers; open finalization remains represented in engine.result until a record is prepared. Missing model-answer exposure/open retry history stays not_captured.
Only the new recovery snapshot module and these notes are added. Existing UI, save controller/builders/repository/schema, engines, fixtures, dependencies and workflows are unchanged. No checkpoint is written, no pending record becomes durable and no recovery behavior is claimed complete.
