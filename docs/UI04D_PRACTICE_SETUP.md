# UI-04d part 1 — practice question selection
Adds a pure choice-question selector before the setup-screen integration. Callers supply a trusted contextual pool with domain/track IDs derived from the question's primary concept; those IDs are not invented as new native question fields.
Filters combine domain, track, level, skill dimension and single/multi/Boolean types. Null means unrestricted for an individual metadata filter; an empty type list selects nothing. Open-response questions are excluded because their subjective flow remains separate. There is no silent fallback to another level, dimension or question type.
Requested sizes are 1 through 100, an explicit implementation limit for this first version. Source order preserves curated pool order. Seeded shuffle uses a deterministic in-memory permutation, not secure randomness, adaptive scheduling or exam balancing. Inputs are not mutated; selected question objects still reference the trusted pool and are snapshotted by the session engine when a session is created.
At most one question from each question family is selected. Source order takes the first matching variant; shuffled order takes the first variant after permutation. Reports distinguish raw matching-question count, available family count, selected count, excluded variants and shortfall. A small bank produces a shorter selection with an explicit shortage, never repeated fillers or fabricated questions.
This selector is not a publication or factual-verification gate. The caller must supply an activated eligible pool for ordinary practice, or explicitly use a labelled fixture pool and pass fixture: true to the session engine. Approval-shaped fields alone do not activate content.
Only the selector and these notes are added. The next small task builds the setup controls and connects their selected question list to the existing engine. Current screens, engines, fixture JSON, dependencies and workflows are unchanged. No storage, hints/confidence, mastery, AI grading or automated authoring is added.
Prepared using contracts already available in the conversation. No repository reads, verification, schema/syntax checks, typechecking, tests, builds, CI inspection or device runs were performed during preparation; none will be performed after pushing. Runtime behavior remains unverified.
