# UI-05c part 2 — choice submission/save integration
Choice sessions and retries adopt the shared native UUID helper. Each successful submit first commits the exact-match answer, captures a save job and displays feedback; then it attempts append-only local fixture-history storage without blocking Next on a storage receipt. Scoring success does not mean save success. Duplicate/stale actions remain guarded by phase, question identity and the rendered session identity.
Preparation failure is distinct from an unconfirmed database save: no controller/save is started for that entry, the committed engine snapshot remains in memory and a retry-capture button can prepare it later. Successful preparation retains one record ID/time/payload through the shared controller. Save cards subscribe independently to ready/saving/saved/unconfirmed/conflict states; retry-save never regrades or substitutes a record ID. Async receipts do not write to the practice component's React state.
Save entries remain visible in active/complete/error branches, including earlier retries in the same mounted selection. Engine restart clears performance answers/signals but keeps those UI save entries; previously confirmed history is not erased. Changing setup/unmounting may hide capture failures and pending receipts, and process restart can lose memory-only jobs. Checkpoint/recovery and a persistent history screen remain pending. No lifetime-first/exposure claim is made.
Practice and Home wording now distinguishes local fixture history from learning progress and avoids saying that every response is unsaved or session-only. The existing demo banner still correctly says progress is not recorded. Saved receipts do not grant approval, mastery or readiness. Both fixture JSON files and native content contracts are unchanged. Open-response saving is not wired by this commit and still follows its previous memory-only flow.
Only the save card's optional label, choice Practice screen, Home wording and these notes change. Engines, record builders, schema/repository/controller, setup/selector, pool/hints, open screen, dependencies and workflows are unchanged. App calls may open/migrate/write the dedicated attempt database only when the new choice submission/save flow is used; no database operation is performed by the assistant here.
