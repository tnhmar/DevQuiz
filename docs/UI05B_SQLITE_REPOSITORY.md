# UI-05b — SQLite schema and append-only attempt repository
Adds source for a dedicated devquiz-attempts.db, isolated from legacy demo databases. Importing the module does not open a database. A future caller explicitly invokes openAttemptRepository, which opens once per module lifetime, enables WAL and applies trusted version-0-to-1 DDL within an exclusive transaction. Newer database versions are rejected; existing version-1 schemas are not silently repaired. No migration or database operation is executed while preparing/pushing this commit.
The schema stores a canonical flat record JSON string plus identity/context/time columns for indexed queries. It enforces unique record IDs and one finalized outcome per session/pack/version/language/question/revision/kind. Choice rows are objective=true, open rows objective=false; fixture remains explicit. Update/delete triggers reject ordinary modification, and a before-insert guard rejects replacement collisions, including INSERT OR REPLACE. No evidence eligibility or publication permission is inferred from storage. Explicit privacy deletion/backup restore needs a separate authorized lifecycle design, not an exposed attempt-delete method.
Append serializes and captures the trusted UI-05a record before queueing. Same record ID and exactly identical canonical headers/snapshot strings return already_saved. A different record under that ID or a second ID for the same logical outcome is a conflict, never an overwrite. RecordedAt and payload must be reused on save retry. Read-by-ID and paginated session history return frozen records. Decode guards basic encoding/context, not full imported-content validity or integrity against external database tampering.
Repository operations are serialized within the singleton, and all transaction statements use the transaction handle and bound parameters. Competing external connections can still produce SQLite lock errors; failures propagate for later UI retry handling and are not labelled saved. Native iOS/Android only for this first implementation; web is explicitly rejected. The connection remains app-lifetime; native reopen/close lifecycle, backup and recovery are later work.
Next: durable session/record IDs, screen save status/error/retry wiring, fixture-specific saved-history wording, interim open submissions and session checkpoints/recovery. Existing UI still does not call this repository and still saves nothing. No existing database, dependency, workflow, engine, screen or fixture is changed by this commit.
Expo SQLite API reference consulted: https://docs.expo.dev/versions/latest/sdk/sqlite/ . Installed-package compatibility and runtime behavior remain unverified.
